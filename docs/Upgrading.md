This page lists what to change in your app when you update `Plugin.AdMob`, newest release first.

## Upgrading from 10.0.120.3

The release after 10.0.120.3 reports load failures that were lost before, including those of ads prepared with `PrepareAd()`, and tells you when the Google Mobile Ads SDK has started.

### Required changes

#### Add `OnAdFailedToLoad` to your own service implementations

`IInterstitialAdService`, `IRewardedAdService`, `IRewardedInterstitialAdService` and `IAppOpenAdService` have a new `event EventHandler<IAdError> OnAdFailedToLoad`. If your app implements one of them itself, for example as a test double, add the event. Mocks generated by a mocking library need no change.

#### Qualify the Android SDK's initialization types

The new `IInitializationStatus` and `IAdapterStatus` in the `Plugin.AdMob` namespace have the same names as types in `Google.Android.Libraries.Ads.Mobile.Sdk.Initialization`. A file that imports both namespaces and uses one of these names, for example to implement `IOnAdapterInitializationCompleteListener` for your own SDK start, fails to build with CS0104. Qualify the name or add a `using` alias, or replace your SDK start with `IMobileAdsService` (see [Waiting for mediation adapters](#waiting-for-mediation-adapters)).

### Clean-up

#### Load failures of prepared ads

The ad services now raise `OnAdFailedToLoad` when the ad requested by `PrepareAd()` fails to load, including an ad that waited for consent. Before, a failed preload looked like one still loading. If you create ads with `CreateAd()` only to see why they fail to load, you can go back to `PrepareAd()` and the service's event.

#### Waiting for mediation adapters

If you start the SDK yourself to see how your mediation adapters initialized, remove that call and await `IMobileAdsService.Initialization`. It completes when the plugin has started the SDK, with each adapter's status. See [Setup](Setup.md#initialization).

### Behavior changes

#### Android and iOS

- An exception thrown while the plugin sends an ad request, for example by the Google Mobile Ads SDK, is now raised as `OnAdFailedToLoad` after `Load()` returns, with the exception's type and message in `IAdError.Message`. This applies to every format, including banners and `NativeAdView`, and to `PrepareAd()` through the service's `OnAdFailedToLoad`. Before, `Load()` threw it if the SDK had already started, and a request held until the SDK had started lost it: neither `OnAdLoaded` nor `OnAdFailedToLoad` was raised, and nothing was logged. If you catch exceptions from `Load()` to handle failed requests, handle `OnAdFailedToLoad` instead.

#### Android

- A native ad's `OnAdFailedToLoad`, also as forwarded by `NativeAdView`, now passes the `INativeAd` as `sender` instead of an internal object, like the native ad's other events.

#### Windows and Mac Catalyst

- `Load()` now raises `OnAdFailedToLoad` ("Ads are only supported on Android and iOS.") on the main thread after it returns, instead of inside `Load()`, so a handler that retries with `Load()` or `PrepareAd()` no longer recurses.

## Upgrading from 10.0.120.2 and earlier to 10.0.120.3

10.0.120.3 moves Android from the legacy Google Mobile Ads SDK v24 (`Xamarin.GooglePlayServices.Ads.Lite` 124.0.0.8) to the Google Mobile Ads Next-Gen SDK (`Xamarin.Google.Android.Libraries.Ads.Mobile.Sdk` 1.5.0), for every ad format. Google [deprecates v24](https://developers.google.com/admob/android/deprecation) on 2027-06-30, when technical support ends but ads still serve, and sunsets it on 2028-06-30, after which its ad requests are at risk of returning no fill. iOS stays on `Jc.GMA.iOS` 12.10.0 and `Jc.UMP.iOS` 2.7.5 and needs no changes, and the plugin's cross-platform API is unchanged.

These notes cover the changes since 10.0.120.2. If you're upgrading from an older version, also read the [release notes](https://github.com/marius-bughiu/Plugin.AdMob/releases) of the versions in between.

### Required changes on Android

#### Set the minimum Android version to 24

The Next-Gen SDK requires API 24; 10.0.120.2 needed 23. Raise the Android `SupportedOSPlatformVersion` in your app's `.csproj` to 24.0. If you followed the [setup guide](Setup.md#android-setup) for 10.0.120.2 or earlier, change the 23.0 in this `PropertyGroup`:

```
<PropertyGroup Condition="'$(TargetFramework)' == 'net10.0-android'">
	<SupportedOSPlatformVersion>24.0</SupportedOSPlatformVersion>
</PropertyGroup>
```

Changing only the 21.0 that MAUI's app template sets in the first `PropertyGroup` doesn't help then, because MSBuild uses the last value the project sets. If your project has no such `PropertyGroup`, change the template's value, or add the one above at the end of the project.

A lower value fails the build in the manifest merger with `uses-sdk:minSdkVersion 23 cannot be smaller than version 24 declared in library`. This drops support for devices on API 23.

#### Raise `Xamarin.AndroidX.Fragment.Ktx` to 1.9.1

The plugin now depends on `Xamarin.AndroidX.Fragment.Ktx` 1.9.1. If your app references an older version, for example 1.8.9.4 from the [NU1608 workaround](Troubleshooting-Android.md#nu1608-warnings-detected-package-version-outside-of-dependency-constraint), restore fails: with NU1107 (version conflict for `Xamarin.AndroidX.Fragment`) on 1.8.x, or NU1605 (package downgrade) on 1.9.0. Raise it to 1.9.1 or remove it; the rest of that set can stay.

```
<ItemGroup Condition="'$(TargetFramework)' == 'net10.0-android'">
	<PackageReference Include="Xamarin.AndroidX.Fragment.Ktx" Version="1.9.1" />
</ItemGroup>
```

#### Raise other Google and AndroidX packages you reference

The Next-Gen SDK brings newer Google and AndroidX packages, for example `Xamarin.Google.UserMessagingPlatform` 4.0.0.4, `Xamarin.GooglePlayServices.Basement` 118.12.0, `Xamarin.AndroidX.Work.Runtime` 2.12.0 and `Xamarin.Google.Guava.ListenableFuture` 9999.0.0. If restore reports NU1605 or NU1107 for a package your app references directly, raise that reference to the version in the message, or remove it.

#### Remove packages that depend on the legacy SDK

The Next-Gen SDK can't be combined with the legacy SDK. If your app references a binding of the legacy SDK, directly or through another package such as a mediation adapter, the build fails with XA4215 (`The Java type ... is generated by more than one managed type`). The message names the assembly that defines the same Java types as `Xamarin.Google.Android.Libraries.Ads.Mobile.Sdk`, for example `Xamarin.GooglePlayServices.Ads.Lite`, `Xamarin.GooglePlayServices.Ads.Api` (from `Xamarin.GooglePlayServices.Ads` 125.x) or `Anjo.Android.GoogleServices.Ads` (from the Anjo mediation adapters). `dotnet nuget why <your project> <that package>` shows which package brings it in. A direct `Xamarin.GooglePlayServices.Ads.Lite` reference may come from the [duplicate Compose classes fix](Troubleshooting-Android.md#build-fails-due-to-duplicate-classes-measurement--compose--etc) for plugin 3.0.2 and earlier; remove it.

The Next-Gen SDK includes the adapter API that mediation adapters build on (`com.google.android.gms.ads.mediation`), so use adapter packages that don't depend on the legacy SDK. `AdMaui.MetaAdapter.Android` 6.21.0 bundles only the adapter and Audience Network, so it builds with this release and the Audience Network SDK loads. Serving Meta ads through mediation hasn't been verified yet ([`#110`](https://github.com/marius-bughiu/Plugin.AdMob/issues/110)). The Anjo mediation adapters depend on the legacy SDK and don't work with this release.

#### Port code that uses the legacy SDK

The plugin no longer brings `Xamarin.GooglePlayServices.Ads.Lite`, so Android code that uses its types directly, such as `Android.Gms.Ads.MobileAds`, `Android.Gms.Ads.AdView` or `Android.Gms.Ads.RequestConfiguration`, no longer compiles. Port it to the Next-Gen binding, in the `Google.Android.Libraries.Ads.Mobile.Sdk` namespaces, using Google's [Next-Gen migration guide](https://developers.google.com/admob/android/next-gen/migration). The `Google.Android.Gms.Ads.*` types in the same package exist for mediation adapters and don't replace the legacy API. This also applies to:

- the `Android.Gms.Ads.Workarounds` load callbacks that the plugin's Android assembly exposed, which are removed;
- code that casts the `PlatformView` behind a `BannerAd`, `NativeAdView` or `MediaView`: these are now the Next-Gen `AdView`, `NativeAdView` and `MediaView`.

### Clean-up

#### Android manifest

Remove any `com.google.android.gms.ads.AdActivity` entry from `Platforms/Android/AndroidManifest.xml`, whatever its attributes. Earlier versions of the [setup guide](Setup.md#android-setup) had you add this one:

```
<activity android:name="com.google.android.gms.ads.AdActivity" android:configChanges="keyboard|keyboardHidden|orientation|screenLayout|uiMode|screenSize|smallestScreenSize" android:theme="@android:style/Theme.Translucent" />
```

The Next-Gen SDK doesn't have that class and declares its own activity for full-screen ads, `com.google.android.libraries.ads.mobile.sdk.common.AdActivity`, so the entry is unused. If you customized it, for example its theme or orientation, apply that to the new activity instead.

Keep the `com.google.android.gms.ads.APPLICATION_ID` meta-data. The plugin reads your app ID from it and passes it to the Next-Gen SDK, and the UMP SDK that handles consent still reads it from the manifest.

Your merged manifest's permissions change too. The Next-Gen SDK adds `android.permission.READ_BASIC_PHONE_STATE`, a normal permission granted at install, and the ads SDK no longer brings the `ACCESS_ADSERVICES_AD_ID`, `ACCESS_ADSERVICES_ATTRIBUTION` and `ACCESS_ADSERVICES_TOPICS` permissions the legacy SDK declared. Check your Play Console permission and Data safety declarations.

#### Starting the SDK yourself

If you start the SDK yourself (`MobileAds.Initialize` on Android, `MobileAds.SharedInstance.Start` on iOS), for example to wait for mediation adapters, you can remove the call: the plugin now holds ad requests until the start, including adapter initialization, has completed. On Android, the legacy `MobileAds.Initialize` no longer compiles.

#### Firebase

The Next-Gen SDK doesn't depend on `Xamarin.GooglePlayServices.Measurement.*`, so the [Firebase measurement alignment](Troubleshooting-Android.md#build-fails-due-to-duplicate-classes-measurement--compose--etc) only applies to 10.0.120.2 and earlier.

### Behavior changes

#### Android

- `BannerAd.OnAdSwiped` is no longer raised: the Next-Gen SDK has no swipe event for banners. iOS never raised it, and native ads on Android still raise `OnAdSwiped`.
- `INativeAd.VideoClickToExpandEnabled` reports what was requested through `VideoOptions.ClickToExpandRequested`, and is `false` for an ad created without video options: the Next-Gen SDK doesn't expose the loaded ad's state. iOS still reports the actual state.
- A native ad's `OnAdImpression`, `OnAdClicked`, `OnAdSwiped`, `OnAdOpened` and `OnAdClosed` now reach handlers attached after `Load()`, including those of a `NativeAdView` created from an already loaded `INativeAd`. 10.0.120.2 only raised them for handlers attached before `Load()`.
- Full-screen ad events, including `OnAdFailedToLoad` and `OnUserEarnedReward`, and a native ad's `OnAdImpression`, `OnAdClicked`, `OnAdSwiped`, `OnAdOpened` and `OnAdClosed`, also as forwarded by `NativeAdView`, now pass the ad (`IInterstitialAd`, `INativeAd`, …) as `sender` instead of an internal object.

#### Android and iOS

- Ad requests are held until the Mobile Ads SDK has started, so the first ad of each launch waits for the start. That's usually a couple of seconds, and a slow mediation adapter can make it longer. On iOS this fixes ads requested at launch, such as the first page's banner or a `PrepareAd()` call, failing with `Request Error: Invalid request.` when the start took more than about 10 seconds. A request whose response is slow can still fail that way, because Google Mobile Ads 12 reports request timeouts as `Invalid request`.
- On iOS and on Android 11 (API 30) and later, a `BannerAd` with the default `SmartBanner` size spans the width of the window's safe area instead of the screen width. On every version it loads a new ad when that width changes, for example after a rotation. While the new ad loads, the banner is empty and `IsLoaded` is `false`; then `OnAdLoaded` or `OnAdFailedToLoad` is raised again. Fixed sizes don't reload. If you bind a banner's `IsVisible` to `IsLoaded`, see [Adaptive banners](Banner-ads.md#adaptive-banners).
